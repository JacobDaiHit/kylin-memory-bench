# 三个可核验的失败案例

以下案例来自标准集运行 `dc318856-004f-4b1c-9910-2ab94d6b2633`，不是人为构造的示意输出。点击链接可查看完整原始提示、回应、记忆和判分规则。结论仅针对本次固定模型、工具和协议下的系统组合。

## 相近项目被误当作更正

Hermes，第一轮，disambiguation-001-224906。

- 事件 28 先保存“星河-001-224906”的格式 Markdown-6234。
- [事件 30](../examples/openkylin-core/evidence.html#event-30) 收到另一个项目“星河归档-001-224906”的格式后，回复明确表示已替换此前记录。可见记忆也只剩归档项目。
- [事件 34](../examples/openkylin-core/evidence.html#event-34) 查询第一个项目时，返回了归档项目的旧约定-001-224906。
- 对第二个项目的查询则正确，构成了项目范围混淆的正负对照。

这里既有写入阶段的错误替换说明，也有后续错误回答的证据。可见现象是将不同项目当作同一信息的修订；不能单凭此案例把根因归到某个具体检索算法或数据库模块。

## 撤销请求被转为额外确认

Hermes，第三轮，update-005-401193。

正式更正与随后召回都成功。用户接着明确要求删除该项目的默认语言并停止保留或复用。[事件 920](../examples/openkylin-core/evidence.html#event-920) 却要求选择删除方案，并说明尚未修改记忆。可见快照仍含简体中文-2606；[事件 921](../examples/openkylin-core/evidence.html#event-921) 再次查询时也返回这个值。

因此存储检查为 wrong_persistence，后续行为为 stale_memory。虽然快照部分可见，但已经观察到禁存值，足以否定“值不再保留”；无需假装看到了所有存储。

这个判分描述的是当前一次性撤销任务没有完成。若某产品设计上必须二次确认，应另立对所有系统一致的多步确认实验，不在看到成绩后只为一个系统删除困难检查。

## 回答语义正确，接口格式不合约

OpenClaw，第一轮，update-005-401193。

[事件 252](../examples/openkylin-core/evidence.html#event-252) 的可见记忆只剩项目标题。随后 [事件 257](../examples/openkylin-core/evidence.html#event-257) 在正确的 `{"answer":null}` 前又写了一段英语解释。

题目明确要求只返回 JSON 对象；评分器不从解释文字中截取一个 JSON 片段，所以该项为 invalid_response。这是输出契约失败，不能据此声称智能体仍记得旧值或忘记操作没有执行。全局存储删除仍只能给 unknown，因为当前快照不完整。

## 对改进的启示

项目身份需要精确约束，更新操作应确认作用域；撤销协议需要区分授权与二次确认；结构化输出应在接口层验证。上述是从本次证据推导的改进方向，不是未经实验验证的性能提升承诺。全量失败和未知项仍以报告中的逐项记录为准。
